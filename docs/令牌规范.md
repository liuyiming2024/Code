# 令牌规范：公共密钥与私有密钥

> 编写者记于 2026-10-12，依据用户定的规矩。

## 两把令牌

| | **公共密钥**（A） | **私有密钥**（B） |
|---|---|---|
| 谁可以用 | **所有 AI 角色** | **仅本项目的负责 AI** |
| 职责 | 读别人的项目 | 读写自己负责的项目 |
| 权限 | 只读 | 读 + 写 |
| 仓库范围 | 全部（含 Chat、Tool） | 自家项目，**刻意不含 Chat** |
| 公开性 | 公开是设计意图 | **绝不可公开** |

**日常一律用公共密钥。** 只有本项目的**负责 AI** 要落盘时，才用私有密钥。

## 为什么按【项目归属】分，而不是按权限高低分

两把令牌覆盖的仓库不同，这不是同一批仓库的两档权限：

- **公共密钥存在的意义是跨项目读取。** 典型是 Chat：
  要看它的账号系统怎么实现，才能决定云盘怎么复用它 —— 但绝不该去改它。
- **私有密钥存在的意义是在自家项目落地改动**，且明确绕开 Chat。

所以"公共密钥为什么不能写"是个伪问题 —— 它本来就不是拿来写的。

> 编写者注：我一开始理解成"同一批仓库、两档权限"，于是纠结 A 为什么不能写。
> 错的。是按项目归属分。

## 实测分工（2026-10-12）

| 仓库 | 归属 | A 读 | B 读 | B 写 |
|---|---|---|---|---|
| Code | 自家 | 可读 | 可读 | 可写 |
| assets / pages | 自家 | 可读 | 可读 | 可写 |
| Tool | 共用指挥部（**私有库**） | **读不到（规则使然）** | 可读 | 可写 |
| **Chat** | 别人家 | **可读** | 可读 | **不可写（403，刻意）** |

- **Chat 不可写是防线，不是配置遗漏。** 账号系统与共享用户表在那儿，
  本项目不改动它 —— 就算某个角色跑偏也碰不到账号系统。
- **公共密钥读不到 Tool 不是缺口，是规则使然。** Tool 是私有库，
  按上一条（公共密钥只覆盖公开库）它本就不在公共密钥的范围内。
  要读它，用**私有密钥** —— 这是设计如此，不是配置遗漏。

## 为什么公共密钥只覆盖公开库

> 用户 2026-10-12 的原话整理，这是**偷懒换来的安全**，不是拍脑袋定的。

**读私有库这件事，交给各自的私有密钥。**

理由有三条，都指向同一个结论：

1. **私有库里装的主要是开发层面的东西。** 而开发者本来就有自己的私有密钥 ——
   要用，用自己的那把就行，不必再给公共密钥开一道口子。
2. **GitHub 的规则在帮我们。** 生成令牌时若**只选公开库**，权限默认就是
   **Read-only**，什么都不用配；一旦勾了私有库，就必须逐项配置详细权限。
3. **详细配置是事故温床。** 每多一个要勾的框，就多一次勾错的机会 ——
   把 Read 勾成 Read and write，表面看不出问题，只在出事那天才暴露。

所以：

| 要访问 | 用哪把 |
|---|---|
| 公开库 | 公共密钥（默认只读，零配置） |
| 私有库 | 各开发者自己的私有密钥 |

**结论：公共密钥不覆盖私有库。** 少配一项，就少一个可能配错的地方。

## 不要给公共密钥补私有库

曾经想给公共密钥加上 Tool（共用指挥部，角色设定 + 协作区在那儿）。
**不做了** —— Tool 是私有库，按上面的规矩它归私有密钥管。

在令牌设置里勾上私有库会**强制要求逐项配置权限**，
而我们的整个设计就是为了避开这一步。不为读一个库破坏这条原则。

**要读 Tool，用私有密钥。**

## 读不到一个仓库时，先问它是公开还是私有

排查顺序，别跳步：

1. **这仓库是公开库还是私有库？** ← 先问这个
2. 私有库 → 公共密钥读不到是**正常的**，换私有密钥
3. 公开库还读不到 → 才是配置问题，去令牌的 Repository access 里勾上

> 教训：我把 Tool 的"读不到"当成配置缺口，催了三轮要补。
> 其实第一步就该问它是私有库 —— 那一步问了，后面三轮都省了。
> **"读不到"不等于"配错了"，可能是"本来就不该读到"。**

## 怎么判断一把令牌到底能不能写

**不要看 `/repos/{owner}/{repo}` 返回的 `permissions` 字段。**
它反映的是"你作为 owner 对该仓库有什么权限"，**不是令牌的权限** ——
用它判断会得出错误结论（所有令牌看起来都 push=True）。

可靠办法是实际试一次写：创建游离 blob（不挂任何分支、不改任何文件）：

```
POST /repos/{owner}/{repo}/git/blobs
{"content": "<base64>", "encoding": "base64"}
```

返回 201 → 可写；403 → 只读。blob 是游离对象、不被引用、会被自动回收，
所以这个探测是安全的。

## 术语：这里的"人"都指 AI

本项目由 AI 编写 —— 人类这边擅长算法与竞赛，开发工作交给 AI。
所以文档里出现的**"负责人""某人""谁"这类代称，实际指的都是 AI 角色**，
不是人类用户。

`Tool/roles/` 下的是各个 AI 角色的设定，"本项目的负责 AI"
指被指派负责该仓库的那个角色（Code 这边是编写者）。

这条要说清楚，否则会把"谁该持有私有密钥"理解错 ——
它不是给人类用户的钥匙，是给负责 AI 的钥匙。

## 安全边界

- **私有密钥一旦在对话、截图、日志里明文出现，立即吊销重新生成。**
  它有写权限，泄露的后果是别人能改你的项目。
- 公共密钥公开是设计意图，泄露影响有限（只读） —— 但仍建议定期轮换。
- 有效期设 30–90 天，不要选"永不过期"。
- 复制时不要带首尾空格，那会导致 401。

## 命名

```
code-public    公共密钥（所有 AI 用）
code-private   私有密钥（本项目的负责 AI 用）
```
