# 诱饵（canary）说明

安全测试时埋的假密钥，用来判断对方能摸到哪一层。

## 三层对照

| 层 | 位置 | 诱饵值前缀 | 报出来说明什么 |
|---|---|---|---|
| ① 仓库 | `security/canary.env` | `canary_repo_` | **只说明他能读这个公开仓库**，不算攻破 |
| ② 数据库 | `code/supabase/canary.sql` 跑出来的那行 | `canary_db_` | **真攻破**：绕过了表级撤权 + RLS + 函数门禁 |
| ③ 环境变量 | Supabase Secrets（不在仓库里） | `canary_env_` | **真攻破**：拿到了部署侧配置 |

## 最重要的一句

**第 ① 层不代表任何东西。** 仓库本来就是公开的，任何人打开 GitHub 都能看到。
只有 ②③ 才是有效信号。

不然你会把"他读了 GitHub"误判成"系统被攻破了"。

## 怎么测

1. 跑一次 `code/supabase/canary.sql`（建数据库诱饵行）
2. 部署函数并用 `supabase secrets set CANARY_DEEP=canary_env_...` 设第③层
3. 让对方尝试获取
4. 让他报出看到的**原文**
5. 对照前缀判断他摸到哪一层

## 硬保护（关键）

**诱饵绝不会被当成真密钥用。** 服务端函数 `oj-cred` 在取密钥时检查
`canary_` 前缀，命中直接拒绝启动并报 `CANARY_KEY_REFUSED`。

为什么必须做死这一步：诱饵值是公开写在仓库里的。
一旦被误部署，就等于用一把全世界都知道的密钥去加密所有人的凭据——
**那比不加密更糟，因为界面上还写着"已加密存储"**。

## 测完记得清理

```sql
delete from public.oj_cred where user_id = '00000000-0000-0000-0000-00000000cafe';
```

## 别被误导的两点

- 诱饵**不能证明**系统安全：对方没找到，可能只是没认真找
- 诱饵被找到也**不等于**真实凭据泄露了：真密钥在环境变量里，不在仓库里
