# 令牌规范：一人两把，只读 / 可写分离

> 编写者记于 2026-10-12，依据用户定的规矩。

## 规矩

**每个参与协作的人（或每个 AI 角色）持有两把令牌，按【项目归属】分工，不是按同一批仓库的权限高低分档：**

| 令牌 | 职责 | 范围 | 权限 |
|---|---|---|---|
| `*-ro`（A） | **读别人的项目** | Chat 等不属于自己负责的仓库 + 共用指挥部 Tool | 只读 |
| `*-rw`（B） | **对自己权限内的项目读写** | 自己负责的仓库（Code / Tool / assets / pages） | 读 + 写 |

关键在于两把令牌的**覆盖范围不同**，而不是同一批仓库给不给写：

- A 存在的意义是**跨项目读取** —— 典型是 Chat：要看它的账号系统怎么实现的，
  才能决定云盘怎么复用它，但绝不该去改它
- B 存在的意义是**在自家项目里落地改动**，且明确**不含 Chat**

**日常一律用 A。** 只在自己负责的项目要落盘时才切 B。

> 编写者注（2026-10-12）：我一开始理解成了"同一批仓库、两档权限"，
> 于是去纠结 A 为什么不能写。错的。用户的原意是**按项目归属分**：
> A 用来读别人家（含 Chat），B 用来读写自家且刻意绕开 Chat。

## 为什么分两把

一次误操作的破坏力完全不同：

- `ro` 用砸了 → 最多读不到东西，**不会破坏任何已有内容**
- `rw` 用砸了 → 可能**整块覆盖别人的改动**

而只读操作占绝大多数（看设定、看协作区、确认线上状态），
却常被顺手配成可写——风险被无谓地放大了。

**本项目真实教训**：编写者曾用一次读取的快照当事实，
把前辈正在推送的改动整块覆盖掉。那次若用的是 `ro`，事故根本不会发生。

## 命名

```
<角色名>-ro    例：code-writer-ro
<角色名>-rw    例：code-writer-rw
```

命名统一，才能在吊销时一眼认出该删哪把、留哪把。

## 仓库范围

按需最小化，不要图省事全勾：

- `ro`：通常需要加 **Tool**（角色设定与协作区在那儿）+ 自己负责的仓库
- `rw`：**只给**自己负责的仓库，**不给 Tool**

Tool 是共用的指挥部，存放角色设定与协作区。
任何单个角色都不该有它的写权限——要改设定是负责人或对应角色自己的事。

### 两把令牌的实测分工（2026-10-12）

| 仓库 | 归属 | A 读 | B 读 | B 写 |
|---|---|---|---|---|
| Code | 自家 | ✅ | ✅ | ✅ |
| Tool | 共用指挥部 | **❌ 缺** | ✅ | ✅ |
| assets | 自家 | ✅ | ✅ | ✅ |
| pages | 自家 | ✅ | ✅ | ✅ |
| **Chat** | **别人家** | ✅ | ✅ | **❌ 403（刻意）** |

- **A 能读 Chat** —— 这正是它存在的意义：看账号系统怎么实现，好让云盘复用它
- **B 不能写 Chat** —— 这是防线。Chat 里是账号系统与共享用户表，
  本项目不改动它，所以 `rw` 令牌刻意不授予写权限
- **A 缺 Tool** —— 这是唯二待补的缺口。Tool 是共用指挥部（角色设定 + 协作区），
  属于"别人的项目"，按分工该由 A 来读。缺了它，日常读协作区就得动用 B，越级了

### 实测：怎么判断一把令牌到底能不能写

**不要看 `/repos/{owner}/{repo}` 返回的 `permissions` 字段。**
那个字段反映的是"你作为 owner 对该仓库有什么权限"，**不是令牌的权限** ——
用它判断会得出错误结论（所有令牌看起来都 push=True）。

可靠办法是**实际试一次写**：创建一个游离 blob（不挂到任何分支、不改任何文件）：

```
POST /repos/{owner}/{repo}/git/blobs
{"content": "<base64>", "encoding": "base64"}
```

返回 201 → 可写；403 → 只读。blob 是游离对象，不会被引用，会被自动回收，
所以这个探测是安全的。

**2026-10-12 实测两把的结果：**

| 令牌 | 可读 | 可写 |
|---|---|---|
| A | Code / Chat / assets / pages（**不含 Tool**） | 否（403） |
| B | 五个仓库全含 Tool | **是，但不含 Chat** |

**B（`rw`）的边界是刻意的：除 Chat 外都可写。**

| 仓库 | B 读 | B 写 |
|---|---|---|
| Code | ✅ | ✅ |
| Tool | ✅ | ✅ |
| assets | ✅ | ✅ |
| pages | ✅ | ✅ |
| **Chat** | ✅ | **❌ 403** |

Chat 是账号系统所在的仓库，云盘的登录态复用它、它的用户表是共享的。
**本项目不改动 Chat**，所以 `rw` 令牌刻意不授予它写权限 ——
这是防线，不是配置遗漏：就算某个角色跑偏，也碰不到账号系统。

待办：**给 A 补上 Tool 的只读权限。** 这是唯一缺口。

## 其他

- 有效期设 30–90 天，不要选"永不过期"
- 令牌只在生成那一屏显示一次，先存进密码管理器再关页面
- 一旦在对话、截图、日志里明文出现过，**立即吊销重新生成**
- 复制时不要带首尾空格，那会导致 401
