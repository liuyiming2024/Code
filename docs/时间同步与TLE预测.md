# 时间同步与 TLE 预测

> 超时（TLE）是竞赛里最贵的一类错：逻辑全对，只是慢了，交上去一片红，而本地怎么跑都发现不了。

## 为什么需要"时间同步"

本环境是**解释器**，不是编译器。它跑一步的代价和真实 C++ 差几个数量级。

| | 每秒能跑 |
|---|---|
| cpplite（本环境）| 约 500 万步 |
| 真实 C++ -O2 | 约 1e8 次基本操作 |

**如果直接把"我跑不动"当成"你的算法太慢"报出去，用户得到的结论就是错的。**

改之前，`n=200000` 的 `O(n)` 循环会被中断并提示"可能存在死循环"——而它在真实 C++ 里只要 **2 毫秒**。

**用自己的能力上限冒充用户的错误，是最坏的一类错。**

## 换算依据（实测标定，非估计）

| 项 | 值 | 怎么来的 |
|---|---|---|
| cpplite 每循环迭代 | **12 步** | 实测：n=1e4 求和 120010 步，n=2e4 → 240010 步 |
| 真实 C++ -O2 | **1e8 次/秒** | 竞赛通用口径；本机实测依赖链约 2.75ns/迭代，量级吻合 |
| → 1 真实秒 | **1.2e9 cpplite 步** | 12 × 1e8 |

Python 单独标定（共用系数会差十几倍）：

| 项 | 值 |
|---|---|
| pylite 每循环迭代 | **4 步** |
| 真实 CPython | **1.86e7 次/秒**（实测 n=1e7 循环 537ms）|
| → 1 真实秒 | **7.4e7 pylite 步** |

Python 比 C++ 慢约 **16 倍**（常识认为慢 10~50 倍，吻合）。

标定环境：g++ 11.4.0 -O2 / CPython 3.10，2026-10-13。**换机器不改变数量级结论。**

## 三件事

### 1. 每次运行显示"等效真实耗时"

不只报步数——步数是解释器自己的量，跟真实 OJ 对不上。现在显示：

```
结束，2,400,010 步（≈ 真实 C++ 2.00 毫秒）
```

### 2. 中断时说清是谁的问题

措辞已从"可能存在死循环"改为：

> 本环境已跑满 X 步（相当于真实 C++ 约 Y），停止执行。
> **这不代表你的程序会超时** —— 本环境是解释器，比真实编译器慢几个数量级。
> 要判断会不会 TLE，请用「TLE 预测」按目标规模外推。

步数上限同时从 200 万提到 **5000 万**（原值只相当于真实 1.7 毫秒）。

### 3. TLE 预测：小规模外推

**为什么不硬跑**：真实 1 秒 = 1.2e9 步，解释器每秒只跑几百万步——物理上不可能在这里"跑满 1 秒"来测试。硬跑只会跑不完然后被误判。

**正确做法**：

1. 从很小规模起步（50、100、200… 自适应翻倍）跑两次，测步数
2. 阶数 `k = log(S2/S1) / log(n2/n1)` → `k≈1` 是 O(n)，`k≈2` 是 O(n²)
3. 外推 `S(target) = S2 × (target/n2)^k`
4. 换算成等效真实秒，与时限比较

> 探测规模必须**自适应**。第一版写死 n=1000/2000，结果 `O(n²)` 在探测阶段就跑满了 5000 万步——探测本身先把解释器拖垮了。

**入口**：命令面板 → 「TLE 预测（会不会超时）」（C++）

## 实测数据

| 算法 | n=1e5 时 | 1 秒内最大 n |
|---|---|---|
| O(n) | 1.00 毫秒 | ≈ 1.0e8 |
| O(n log n) | 13.83 毫秒 | ≈ 4.5e6 |
| O(n²) | 1.2 分钟（TLE）| ≈ 11,574 |
| O(n³) | 110766 分钟（TLE）| ≈ 514 |

与竞赛常识吻合：`O(n²)` 上限约 1e4，`O(n³)` 上限约 500。

## 局限（如实列出）

- 假设程序从输入读**第一个整数**作为规模 n
- 若两次步数几乎相同（耗时与规模无关），会**如实说无法外推**，不编造结果
- 分治、递归等复杂形态可能拟合不准
- 常数因子差异（如 `vector`  vs 裸数组）不体现在阶数里
- Python 侧目前只显示等效时间，外推预测仅 C++ 可用
