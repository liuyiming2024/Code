## 🔴 两件必须先知道的事

### 1. Ruby 跑不通，是已知限制，不是 bug

`ruby-wasi.js` 是 **ESM 构建**，classic Worker 的 `importScripts` 加载不了 ESM。
而 module Worker 又不兼容 UMD 资源（sql.js / pyodide / clang 全是 UMD 或 Emscripten 输出）——
两者不能兼得，当前选了 classic。

`runRuby()` 会明确抛错说明原因，**不静默失败**。

要修，二选一：

- 抓 `@ruby/wasm-wasi` 的 **IIFE 版**（`browser.script.iife.js`）。试过的路径都 404，得先找到正确路径
- 或者给 Ruby 单独起一个 module Worker，与现有 classic Worker 并存

### 2. 没有做过端到端验证

开发环境的出站请求被网络策略挡住，访问 GitHub release 下载返回 403。
所以**六语言的实际加载与执行一次都没真跑过**，只有结构断言（47 项全过）。

请先在真机验证最轻的那个：

```
打开 Code → 新建 t.sql → 写：
CREATE TABLE t(a); INSERT INTO t VALUES(1); SELECT * FROM t;
点运行
```

0.7 MB，几秒完成。**它通了就说明整条链路是好的**（下载 → 缓存 → Worker → 执行），
剩下五个只是体积与耗时的差别。

## 两个设计决定，改之前请先读

### 接管了 Worker 里的 fetch

`rt-worker.js` 里 patch 了 `self.fetch`：凡是我们资源前缀的请求都先查 Cache Storage。

**为什么**：pyodide 拿到 `indexURL` 之后会自己去 fetch `pyodide.asm.wasm` 和 stdlib，
sql.js 的 `locateFile` 同理 —— 不接管的话，它们会绕过缓存每次重新下载。

改动这块前先想清楚，去掉会导致缓存形同虚设。

### 用 classic Worker，只用 UMD 资源

module Worker 不支持 `importScripts`。资源抓的全是 UMD / Emscripten 输出。

代价就是 Ruby（只有 ESM）暂时接不上。上面说过。

## 三条不能省的约束

1. **运行时只在 Worker 里跑。** clang.wasm 40 MB，主线程编译会白屏好几秒
2. **必须显示下载进度。** 用户主动点了运行，就得知道在下什么、还剩多久
3. **首次需要联网。** 之后走 Cache Storage，断网可用。别装作没这一步
